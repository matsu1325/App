## 目標と初期範囲

最初の到達点は、代表的な戦技について、武器・派生・強化・能力値・入力分岐を指定し、各ヒットと1回の行動の推定ダメージ、消費FP、ダメージ/FPを再現できるデータを揃えること。

続いて投射物、複合攻撃、バフへ広げる。DPSは別の検証段階とし、ダメージを計算できるだけでは対応済みにしない。初期の比較条件はPvE・正面の通常命中とする。カウンター、部位特効、PvP、状態異常発症、各種条件付きバフは条件を記録し、それぞれの対応状況を管理する。

対象版はまず現行アプリの1.17パラメータを基準にする。参考シートの1.17.1表記とは区別する。収集開始時に公式パッチ情報と配信データの版を確認し、新しい版があれば別スナップショットとして差分を作る。

## 収集元と役割

1. **Frame Data Explorerの版付き資料**：`https://er-frame-data.nyasu.business/generated/1.17/`以下の`SwordArtsParam.json`、`EquipParamGem.json`、`EquipParamWeapon.json`、`BehaviorParam_PC.json`、`AtkParam_Pc.json`、`Bullet.json`、`SpEffectParam.json`、`FinalDamageRateParam.json`、`animations.json`、`attacks.json`、`armaments.json`。まず既存manifestとハッシュを照合する。補正曲線や強化テーブルが不足する場合は、その版の対応資料を追加する。
2. **行動分岐の資料**：[公開HKS](https://github.com/soulsmods/EldenRingHKS/blob/d88d6441f5fccfdd6a5fd10d493309b680181897/c0000.hks)とアニメーションイベント。構え、追加入力、溜め、反復、FP不足時の分岐を復元する。公開HKSにはコミュニティ編集が含まれるため、ゲーム本体との一致は別途確認する。
3. **コミュニティの数値表**：既存manifestにある[Motion Values](https://docs.google.com/spreadsheets/d/1j4bpTbsnp5Xsgw9TP2xv6d8R4qk0ErpE9r_5LGIDraU/)、[Build Planner](https://docs.google.com/spreadsheets/d/19Op36P7gdVMkPzFQX6OsjZcfyUjdGOj7Cjk9qFAVj-U/)、[Misc Effects](https://docs.google.com/spreadsheets/d/1rfYfa5kcyoCuKgnS23dc8J8lLLTqWXsWtq9qG4TxT50/)を照合候補にする。シート名・行・セル・数式を記録。同じ抽出元に由来する表同士の一致は独立した実機検証ではない。
4. **名称**：既存の日英対応と同一版のメッセージIDで照合。同名の戦技と魔法、同名別IDを名前だけで結合しない。
5. **実機の検証記録**：パッチ、武器、強化、派生、能力値、敵、入力、装備効果が特定できる動画・測定値。Wiki等は確認先の発見に使い、条件不明の最終ダメージをそのまま係数にしない。

出典ごとに取得日時、URL、ゲーム版、ファイルハッシュ、抽出位置、利用条件を残す。既存manifestには再配布条件未確認の資料があるため、原本は保管場所を分け、公開用には利用条件を確認した必要項目・出典・検証結果を用意する。

## 集める項目

| 分類 | 必須項目 |
|---|---|
| 識別・適用範囲 | 戦技ID、戦灰ID、日英名、版、プレイヤー用か、固有武器、装着可能武器・派生・例外 |
| 入力・行動 | L2単発、構え→R1/R2、溜め段階、追加入力、反復、終了動作、持ち方、前提状態 |
| コスト | 始動・追撃・持続ごとのFP/スタミナ、FP不足時の挙動、0FPの扱い |
| ヒット | アニメーション・イベント・攻撃ID、順序、同時/連続、物理属性、属性別MV、固定攻撃値、最終倍率、強靭削り、状態異常倍率 |
| 補正 | 使用する武器AR成分、能力値補正、強化/派生補正、補正曲線、筋力の両手補正の適用条件、能力不足時の処理 |
| 弾・追加効果 | 弾ID、子弾、爆発、生成数、追尾/貫通、同一敵への再命中間隔、接触判定との重複可否、距離・命中条件 |
| バフ | 対象、倍率/加算、適用順、持続時間、消費条件、重複/上書きグループ |
| 時間 | 発生、各判定、追撃受付、次回始動までの周期、速度変化、ヒットストップ、時間単位と根拠 |
| 証拠 | 出典の行/キー、原本ハッシュ、導出式、未解決事項、照合値、実測条件・動画の時間位置 |

戦技ごとに一つの「倍率」へ潰さず、武器攻撃・投射物・固定成分・バフをそれぞれ記録する。近距離で刀身と衝撃波が当たる場合と、遠距離で衝撃波だけが当たる場合は別の命中条件にする。

## 作業手順と成果物

### 0. 原本と版を固定する

- 既存スナップショットを復元し、必要な原本が揃うか監査する。
- 現行版との差を確認し、同じ版の取得物をmanifestにまとめる。
- 戦灰・既定戦技・戦技パラメータを突き合わせ、プレイヤー用、非攻撃、内部/未使用、判別待ちに分類する。
- 成果物：`source-manifest.json`、全件台帳、欠落原本リスト、版差分。

### 1. 第1弾の4戦技を端から端まで結び付ける

- 戦技→入力分岐→行動/アニメーション→判定窓→攻撃パラメータの参照を解決する。どの経路を辿るか自体に根拠を付ける。
- 一つの窓に並ぶ参照は、武器ごとの候補か実際の複数ヒットかを判別する。候補を全部足さない。
- 属性別MV・固定値・最終倍率・FPと、その適用条件を原資料の値とともに保持する。
- 成果物：4戦技の行動別JSON、参照図、サンプル計算、未解決事項。

### 2. 補正式と適用条件を照合する

- 単純な武器MV型と、独自補正・固定成分・投射物型を分類する。
- 装着可能な代表武器を選び、強化0/中間/最大、能力値の低/中/高、代表派生で比較する。未装着の組合せは比較対象にしない。
- 両手時の筋力補正、武器本体の属性と戦技側の属性、能力不足、FP不足の分岐を個別確認する。
- 成果物：補正式の根拠、条件ごとの期待値、外れたケースの差分と理由。

### 3. 投射物・追撃・DLC・バフへ拡張する

- 子弾・爆発・追加効果の参照を辿り、循環検出と探索上限を設ける。生成数と実際の命中数は別の値にする。
- 接触＋弾、追撃あり/なし、溜め、継続使用を別行動として扱う。
- バフの適用順と重複規則を記録し、既存の手動倍率との二重適用を検出できるようにする。
- 第1弾から不足が出た場合も、推測値で埋めず阻害理由付きで残す。
- 成果物：拡張プロファイルと、類型・本編/DLC別の収集率/検証率。

### 4. 実機でダメージを照合する

- 版、周回、敵の個体/形態、武器/派生/強化、能力値、持ち方、装備効果、影樹の加護、距離、入力分岐を固定する。
- 代表ケースは各条件3回以上。各試行の前に敵・バフ・HP条件を戻す。刀身のみ、弾のみ、両方が当たる条件を可能な範囲で分ける。
- 敵防御は各ヒット・各属性に適用してから合算する。状態異常発症分は通常ダメージと分けて測る。
- 表示整数の丸め位置と許容差を検証記録に明記する。一律の「数%以内」を根拠なく合格条件にしない。
- 成果物：版と条件付きの実測記録、予測/実測の差、再現手順。

### 5. 必要な戦技からDPSを検証する

- 始動・追撃・構え待機・終了・次回始動の遷移を確認し、単発ダメージ/行動時間と定常反復DPSを別に扱う。
- 既存記録では配信UIが30資料フレーム/秒を使用している。ただし録画FPS、再生速度、実入力遷移とは区別し、適用範囲を確認する。
- 反復できる行動はウォームアップ後10周期以上×3試行を候補とし、空振りと命中の差も記録する。長い継続技やバフは適した測定窓を別に定義する。
- FP無制限の理論値と、FP予算内の総ダメージを区別する。時間根拠が不足する間はDPSをnullに保つ。
- 成果物：時間の証拠、周期プロファイル、測定誤差、対応指標一覧。

## データ構造の案

原本と正規化データは分ける。正規化レコードは概ね次の構造にする。

```text
skill_id, game_version, name_ja, name_en
availability: ash_ids, weapon_ids, affinity_rules, exceptions
actions[]:
  action_id, input_sequence, conditions, animation_refs
  costs: initial_fp, followup_fp, sustained_fp, stamina, insufficient_fp_behavior
  hits[]: attack_ref, component_kind, damage_formula, physical_type,
          typed_mv, typed_flat, scaling_refs, final_rates,
          hit_conditions, status_mv, poise, provenance
  effects[]: effect_ref, target, duration, stack_group, consumption, provenance
  timing: source_units, unit_evidence, transition_refs, cycle_seconds
  validation:
    mapping, formula, damage, timing, compatibility
    blockers[], evidence[]
```

未知はnullと理由で表し、実際の0と区別する。`damage`が実測済みでも`timing`は未検証を取り得る。ダメージ/FPは、行動に含めた全段のコストが確定し、合計FPが正の場合だけ数値化する。

計画上の保存先は`tools/elden-ring/skills/`（抽出・検証コードと仕様）と`data/elden-ring-skills/`（利用条件を満たす正規化データ・集計）。大きな原本や検証動画は別保管とし、公開側から証拠IDで参照する。

## 完了条件

- 全件台帳の分母が決まり、全候補に状態と未対応理由がある。
- 第1弾の4戦技について、予定した入力分岐の参照・FP・式・代表実測が揃う。足りない分岐は戦技名だけで対応済みとしない。
- すべての採用値から原本の版・ハッシュ・行/IDを辿れる。
- 参照欠落、重複合算、無効な装着、未知値の0変換、版の混在を自動検査できる。
- 同じ原本から同じ正規化データを再生成でき、更新時の差分を出せる。
- ダメージと時間の検証状態を別々に表示でき、DPS未検証の戦技を正確なDPSとして扱わない。

まず段階0〜2の4戦技の試験収集を1つの作業単位にする。そこで未解決率と1戦技あたりの参照解決量を測り、第2弾以降の工数を見積もる。実機測定には、対象版のゲームを操作できる検証環境または条件を満たす録画が必要。
