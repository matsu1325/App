## 結論

攻撃・アニメーションの原資料は既に収集済み。次の作業は新規の大量収集ではなく、武器／魔法ごとの参照解決、遷移の復元、時間単位と周期の検証である。今回の監査でDPS検証済みとなった攻撃は **0件**。公開アプリの計算やソートは変更しない。

## 情報源の採否

1. 主資料：[Frame Data Explorer](https://er-frame-data.nyasu.business/) の `generated/1.17/animations.json`、`attacks.json`、`armaments.json`、`Magic.json`、`Bullet.json`、`BehaviorParam_PC.json`。保存済みスナップショットとハッシュを固定して解析する。パス上の版は1.17であり、1.17.1との全差分は未確認。
2. [公開データリポジトリ](https://github.com/sovietspaceship/elden-ring-frame-data-explorer-data) はREADMEと一覧を確認。ルートに1.06、1.07、1.08、108しかなく、今回の1.17計算用データの代替にはしない。READMEはゲームデータとコミュニティ表から生成と説明している。
3. [TAE差分リポジトリ](https://github.com/EldenRingDatabase/er-animation-data-diff) の既定ブランチ最新コミットは `d26d510738cde477eb27275d803f68b4f2c7b997`、2024-09-11、メッセージ1.14。構造を調べる参考にはなるが、1.17の時間データとして混ぜない。
4. [DSAnimStudio](https://github.com/Meowmaritus/DSAnimStudio) はアニメーションイベントを確認する候補。必要なら適法に取得したゲームデータで照合する。ツールの存在だけで現行版対応や実測済みとはしない。
5. 実機動画は版・フレームレート・装備・入力列が分かるものだけ検証証拠に採用する。今回、周期を裏付ける実機映像は未収集。

保存済みFrame Data資料の再配布条件は未確定。原本一式はリポジトリに追加せず、監査コード・集計・少量の検証例を保持する。アプリへのデータ組込み前に利用条件を確認する。

## 原資料で確認できた落とし穴

### ロングソードの片手R1初段

`a023_030000` は攻撃窓 `[13,16]`、LightAttackOnly `[17,21]`、RightAttack `[21,83]` を持つ。これらは原資料のフレーム値であり、今回秒数には変換しない。

攻撃窓にある `100200000:768` と `100200000:876` は2ヒットではない。前者の対応武器リストはLongsword等、後者はStone-Sheathed Swordで、物理属性もStandardとStrikeに分かれる。対象武器に対応するレコードを選択してからヒットを構成する必要がある。

`cancelFrom` はキャンセル種別で、遷移先アニメーションIDではない。最も早いキャンセル時刻だけを取り出してコンボ周期と断定できない。最終段から次の初段への戻りと、攻撃終了前の打ち切りも確認する。

### 輝石のつぶて

`a401_045000` Startup、`a401_045010` Cast 1、`a401_045020` Cast 2、`a401_045030` Cast 3に関連付く。Cast 1の判定開始12、Magicキャンセル開始22に対し、Cast 2/3は17と27。DexterityCastingSpeed条件も別にある。どの段を連打するか、技量補正がどの区間に作用するかを復元する必要がある。

同じ窓に輝石のつぶて・大つぶて・氷のつぶての候補が並ぶため、ここでも全参照を合算しない。弾生成時刻は敵への命中時刻とは異なる。

## 実装する指標

初期の連続DPSは「FP・スタミナ制約なし、定常状態で同じ行動を反復する理論値」。回復・聖杯瓶・状態異常・条件付きバフは別プロファイルにする。各ヒットの攻撃倍率と敵防御を適用してから合算し、定常周期の秒数で割る。

初回始動を毎周期に足さない。連打が複数段で循環する場合は、その循環全体を分母にする。単発のアニメーション全長や、最初のヒット時刻を分母として使わない。

## 次の作業と合格条件

1. **時間と遷移を確認**：生成元・TAE仕様から原資料の時間単位を確定。描画FPSとデータの時間基準を区別し、速度勾配・ブレンド・入力バッファ・ヒットストップの影響を明示する。最終段→初段を含む連打遷移を証拠付きで定義。
2. **通常攻撃を接続**：Longsword、Dagger、Uchigatana、Greatsword、Twinblade、Backhand Blade、Miladyを最初の検証候補にする。片手／両手、単発／多段、固有モーションを分けて、武器ID→イベント→当該武器の攻撃レコードを解決。候補が複数残る場合は未対応として記録。
3. **魔法を接続**：Glintstone Pebble、Great Glintstone Shard、Swift Glintstone Shard、Catch Flameを検証候補にする。詠唱速度の最小・中間・最大条件、連続入力時の段選択、弾のヒット数を確認。候補名は優先順位であり、対応確定を意味しない。
4. **周期を照合**：版・装備・持ち方・技量／詠唱補正・敵・入力・録画FPSを固定。ウォームアップ後に10周期以上を3試行で測定し、周期とヒット数を照合。開始／終端フレームの読み取り誤差を記録し、差が測定誤差を超えれば検証済みにしない。空振りと命中の差も確認。
5. **ソートへ接続**：承認されたプロファイルのみランキング対象にし、未対応は末尾で「未検証」と表示。0 DPS扱いはしない。防御前理論DPSと対敵ダメージDPSを区別し、使用攻撃・敵・持ち方・詠唱条件・データ版を併記。

将来のプロファイルには `entity_id / action / hand_mode / animation_ids / selected_attack_keys / hit_times / transition_edges / time_base / speed_conditions / cycle_seconds / game_version / sources / validation` を持たせる。`cycle_seconds` が未確定ならnull、`ranking_eligible`はfalse。出血・冷気、戦技派生、持続魔法は別検証後に拡張する。

## 再現

```bash
python tools/elden-ring/audit-dps.py --source-dir /path/to/elden-ring-data --output tools/elden-ring/dps-audit.json
```

元資料は既存の `elden-ring-implementation-data.zip` を展開したフォルダ。監査スクリプトは標準ライブラリのみで動作する。スナップショットの件数と参照存在を検査する処理であり、ゲームのダメージ・DPS検証テストの代替ではない。
